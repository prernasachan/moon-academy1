## 02. Business Problem & Objective

### Business problem

A distributed learning programme can involve multiple activities: maintaining a training catalogue, assigning learning to employees, tracking completion, coordinating instructor-led sessions, processing nominations and following up on overdue items.

When these activities are handled through disconnected lists, emails and manual trackers, employees and administrators may have to navigate multiple places to find information. Progress visibility and follow-up can also become difficult as the number of resources and training records grows.

### Previous/manual process

The supplied application materials do not document a formal before-state process. The following is therefore the operational problem the application is designed to address, not a claim that a specific manual process was measured:

- Training information and employee assignments require a common view.
- Employees need visibility of their own learning status and due dates.
- Administrators need a structured way to maintain training and session records.
- Session nominations require submission and review.
- Training completion and supporting evidence need to be accessible for follow-up.

### Application objectives

1. Provide a centralized employee learning workspace.
2. Give employees visibility into assigned, completed, pending and overdue training.
3. Simplify training discovery through search and filters.
4. Support evidence submission against assigned training.
5. Enable discovery, scheduling and management of learning sessions.
6. Support nomination submission and review.
7. Provide administrators with user, training, session and nomination management capabilities.
8. Make resource-level training records and progress easier to review.

### Example: application initialization

The app initializes the signed-in user, resolves the user's role, loads active training/session data and prepares employee-specific collections.

Simplified illustration based on the source:

```powerfx
Set(varUser, User());

Set(
    varUserRole,
    LookUp(
        VarUserRoleList,
        Resource.Email = varUser.Email,
        Role.Value
    )
);

Set(
    varUserTempRole,
    If(IsBlank(varUserRole), "User", varUserRole)
);

ClearCollect(
    colEmpTrainingRecord,
    Filter(
        MA_EmpTrainingRecords,
        ResourceEMail = User().Email
    )
);

ClearCollect(
    colSessions,
    Filter(
        MA_MasterSessionDetails,
        Date >= DateAdd(Today(), -6, TimeUnit.Months) &&
        SessionStatus.Value = "Active"
    )
);

ClearCollect(
    colTrainings,
    Filter(
        MA_MasterTrainingList,
        Status.Value = "Active"
    )
);
```

This is a readable excerpt of the initialization approach. The original source should be treated as authoritative when reproducing or modifying formulas.

### Example: enriching training records

The app creates a lookup collection that adds the corresponding master training record to each employee training record:

```powerfx
ClearCollect(
    colEmpTrainingRecord_Lookup,
    AddColumns(
        colEmpTrainingRecord,
        MasterRec,
        LookUp(
            colTrainings,
            ID = MasterTrainingID.Id
        )
    )
);
```

This supports displaying employee-specific progress alongside master training information.

### Delegation and performance considerations

The app loads data into collections and performs several filters, lookups, sorting operations and aggregations. For a production-scale deployment, validate:

- Whether each SharePoint query is delegable.
- Whether records beyond the configured data row limit are required.
- Whether collections are appropriate for the expected data volume.
- Whether repeated `LookUp()` operations can be reduced.
- Whether screen-level refresh and collection loading are necessary.
- Whether large galleries should use server-side filtering and pagination patterns.
- Whether the configured data row limit and list indexing support expected volumes.

The package sets `DefaultConnectedDataSourceMaxGetRowsCount` to `2000`; this setting does not by itself prove that every query retrieves all records or is delegation-safe.

### Error handling

The source includes `Notify()` usage and form submission patterns. Validate the actual error branches and user-facing messages before documenting a complete error-handling strategy. Recommended areas to evidence include failed submissions, missing required fields, connector failures and unsuccessful workflow calls.

### Concepts recruiters should look for in the source

- **App lifecycle:** `App.OnStart` initialization, user context and collection loading.
- **Data shaping:** `ClearCollect`, `Filter`, `AddColumns`, `LookUp`, `Distinct` and `SortByColumns`.
- **Business logic:** `If`, `Switch`, status conditions and role-aware behaviour.
- **Data updates:** `Patch`, `SubmitForm` and form validation patterns.
- **Operational metrics:** `CountRows` and filtered counts for dashboard tiles.
- **Reusable UI:** component definitions for shared navigation and profile experiences.
- **Integration points:** named flow/service connections, Teams and Outlook connections.

### Delegation, security and performance considerations

These are important engineering considerations for this solution and should be validated in the target environment:

1. **Delegation:** Review each data-source query for delegation warnings. The use of collections does not remove SharePoint delegation limits from the query that populates them.
2. **Data volume:** Confirm the expected size of employee training, session and nomination records. Avoid loading an unnecessarily large dataset into a client-side collection.
3. **Role security:** Hiding screens or buttons based on a role is not a security boundary. Enforce access at the data source and workflow layers as well.
4. **Collection refresh:** Define when collections are refreshed after create/update operations so that galleries and dashboard metrics do not show stale values.
5. **Repeated lookups:** For large datasets, assess whether repeated `LookUp()` calls can be replaced with a more efficient data-shaping strategy.
6. **Error handling:** Validate connector and form failures, and provide meaningful user feedback through error handling and `Notify()` patterns.
7. **Connection management:** Rebind environment-specific connections and connection references when moving the app to another environment.

The app package sets `DefaultConnectedDataSourceMaxGetRowsCount` to `2000`. This is a client-side data retrieval setting and does not prove that all records are retrieved or that every query is delegation-safe.
